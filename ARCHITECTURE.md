# Architecture

The initial implementation estimate for this challenge was **3 business days**.

## Boundaries and React/PixiJS integration

`options` owns validated `GameOptions` and its local persistence. Each adjustment writes storage before changing React state; a failed write leaves both the displayed and `App` values unchanged. `battle` owns typed balance, simulation, input, asset loading, PixiJS rendering, and the small React HUD sample. `matches` owns `MatchRecord`, browser persistence, API client, and result UI. `menu` owns navigation and remote-record views. `App.tsx` coordinates screens, the immutable options snapshot captured when Play starts, the latest completed record, and pending registration.

React owns menus, forms, dialogs, loading/error states, touch controls, results, and a HUD sample. PixiJS owns ocean, islands, ships, projectiles, effects, and ship health bars. `BattleScreen` creates exactly one `Application`, `GameSimulation`, `InputController`, and `BattleRenderer` per mounted match. Continuous combat state never enters React: React receives only health, score, remaining time, pause, and end state at most once per 100 ms, plus explicit pause and finish updates.

The renderer reads the simulation's mutable `BattleRenderState` once per Pixi ticker frame. A full cloned `GameSnapshot` is produced only for the finish callback and deterministic test bridge. This avoids per-frame entity cloning while preserving immutable snapshots at external boundaries.

Assets load before the canvas and input controller are created. Loading exposes progress; failed texture loading exposes Try Again. On exit, the input controller removes keyboard, blur, and visibility listeners; the renderer removes dynamic display objects and destroys only its derived island textures; then Pixi destroys the application, ticker, stage, and canvas. Shared textures returned by Pixi's asset cache remain available for the next match. The initializer checks disposal after async work so React Strict Mode can mount and clean up safely.

## Simulation, collision, and balance

`gameBalance.ts` is the typed source for the arena, entities, weapons, projectiles, spawns, and gameplay feedback. Options expose session duration and spawn interval; all other values remain centrally adjustable without editing rule logic. A match uses its saved option snapshot, which is also stored on the completed record.

The game runs a fixed 1/60-second simulation step. The ticker accumulates elapsed time, caps recovery after stalls, and runs at most eight steps per rendered frame. Movement, cooldowns, spawns, effects, and timer all use simulated time. Pausing clears input and the accumulator, so lost focus and hidden-tab time cannot create deferred actions. Ending a match stops subsequent simulation steps.

Islands have one collision representation: a 4 by 4 tile land mass modeled as a rounded square. Its half-size and corner radius drive ship correction, spawning clearance, navigation, projectile cover, and the Playwright collision assertion. Ships are clamped to arena bounds and pushed out of the rounded boundary. Enemies navigate around a conservative circle containing each rounded island, choose a persistent side, steer away from edges, and recover if blocked. Projectiles use segment tests against the rounded square and targets, then are removed after their first hit, island contact, expiry, or arena exit. A destroyed enemy is removed before it can act again.

The default arena is 960 by 540. The player has 100 health, moves at 150 units per second, and turns at pi radians per second. Front cannon cooldown is 0.42 seconds; each broadside fires three projectiles with a 1.2-second cooldown. Player projectiles deal one damage, travel at 330 units per second, and expire after 1.6 seconds. Chasers have two health, move at 86 units per second, and deal 25 damage on impact. Shooters have one health, move at 68 units per second, fire within 310 units, prefer 220 units, and deal 12 damage per projectile. Automatic spawning pauses at six living enemies, preserving the time left until the next spawn; it resumes when the count falls below six. The limit excludes the player. These values prioritize readable approach lanes and enough recovery time around the two islands; they are balance decisions, not physical simulation. Pixi draws each ship's frame before a red fill whose width follows its health ratio; the separate React HUD keeps green, amber, and red states.

## Persistence, contracts, cache, and recovery

`pirate-battle.options.v1` stores valid options. `pirate-battle.matches.v1` stores a versioned envelope with a stable player ID, the last completed match, and pending records. Completing a match writes its ID once to both last result and pending queue. A storage failure leaves the in-memory record available for Retry Save.

MSW exposes `GET /api/ranking?config=<key>&page=<n>&pageSize=<2|5>`, `GET /api/matches?playerId=<id>&page=<n>&pageSize=<2|5>`, and `POST /api/matches`; Axios has a 1200 ms request timeout. The mock validates positive pages and page sizes of two or five, defaulting to five if omitted. `MatchRecord`, `Page`, ranking entry, and configuration-key contracts are shared by the API client, fixtures, handlers, storage validation, and UI. The configuration key is canonical JSON of options and full balance, so the changed damage and spawn rules form a separate ranking group while older records remain in personal history. Ranking sorts by score descending, completion time ascending, then match ID ascending. History sorts newest first.

Confirmed mock records live in `pirate-battle.confirmed.v1`. POST uses `matchId` as its idempotency key; a repeated POST returns the already confirmed record. Local completion first persists the pending record, then a single TanStack mutation drains one pending item per recovery cycle. Failure leaves that record pending for explicit retry, reload, reconnect, or scenario recovery. Gameplay never waits for registration.

Ranking query keys include canonical configuration, page, page size, and scenario epoch. History keys include player ID, page, page size, and epoch. Compact viewports request two records per page; desktop requests five. Resizing resets to page one. Desktop pagination uses `keepPreviousData`; compact views load the new page before displaying it so five stale rows cannot force overflow. Request abort signals cancel obsolete fetches, and scenario changes cancel and advance the epoch so delayed responses cannot replace current data. Successful registration invalidates both query families. Query retries are limited to transient failures; POST retry stays explicit because timeout may have committed remotely.

## Verification and limitations

The responsive verification covers desktop and mobile Chromium at 320×568, 667×375, 851×393, and 956×440. Short landscape viewports use compact menus; the desktop battle view exposes a thin gameplay-controls footer, while touch layouts hide that footer.

`?e2e=1` in development stops the ticker and provides a seeded test bridge that advances the real fixed-step simulation. Playwright uses keyboard and pointer events, covers gameplay and recovery flows on desktop and mobile Chromium, asserts no scrolling at 320×568, 667×375, 851×393, and 956×440, and versions visual baselines for menu, Options, arena, red ship bars, impact, and result.

`npm run profile` profiles a production preview in visible Chromium for 180 active seconds. Its harness makes the player invulnerable only so the benchmark reaches its time limit; enemies, projectiles, collisions, effects, and rendering remain active. It records frame intervals, simulation and renderer time, entities, completion state, environment, forced-GC heap readings, and five cleanup cycles. `npm run profile -- --headless` is diagnostic only: the checked-in headless report does not prove the reference performance target. The acceptance target is at least 58 FPS and p95 frame interval of 20 ms or lower on the documented reference desktop, and it is considered validated only by an eligible visible Chromium profile. GPU, heap, or other browser metrics may be unavailable; reports write `null` rather than invent values.

Browser storage can be unavailable. In that case local options or matches report failure and cannot survive refresh. Audio is outside the current gameplay scope. The published Vercel deployment is [https://pirate-game-alfredo.vercel.app/](https://pirate-game-alfredo.vercel.app/); its build uses `npm run build`, outputs `dist`, and is configured by `vercel.json`. The deployed build should be validated for direct navigation, refresh, canvas/assets, the MSW service worker, Ranking, Match History, and completed-match registration.
